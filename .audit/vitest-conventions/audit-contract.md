# Vitest convention audit contract

Applies to every delegated auditor of this workspace. Read it in full before touching a file. Do not edit this file.

## Objective

Make every assigned vitest test file in `extensions/` strictly adhere to `extensions/AGENTS.md`. Read that file in full first. It is the contract; this document only explains how to apply it here.

The mechanical rules are already satisfied (a checker proves it). Your job is the rules a static scan cannot decide.

## Rules that need judgment

For each assigned file, check every one of these against the actual test bodies.

**Test design (unit tests).**
- The test asserts observable behavior of the subject, not its internals: no assertions on private helpers, call counts that only restate the implementation, or values the test itself constructed.
- The subject under test is small and deterministic; the test runs real project code and mocks only external or nondeterministic boundaries.
- Mocks are not overused: if a plain injected function or the real dependency would express the same thing, the mock is the violation. Module mocks only for real boundaries.
- No mock of a same-module private helper.
- Every test covers a case the unit actually handles: happy path, boundaries, empty values, invalid values, dependency failures. A case list that misses the unit's own error branches is a gap.
- Every assertion proves the behavior named by the test name. If the test would pass with every imported function returning `undefined`, the assertion is the violation.
- Assertions are precise: exact literals over truthiness, partial matchers over whole-object equality only when the rest is irrelevant.
- Tests do not leak mocks, globals, env vars, timers, module state, or filesystem state between tests.
- Filesystem access uses a test-controlled temporary directory, never the developer's home, `~/.pi`, or the repository working tree as implicit state.
- `describe` nesting stays shallow; test names are short and name the behavior.

**Integration tests** (`test/integration.test.ts`, `user-perspective.test.ts`, `shells.test.ts`, `workers*.test.ts`, `worker-errors.test.ts`, `worker-review.test.ts`, `context-review.test.ts`, `rpc-*.test.ts`, `cleanup.test.ts` and anything driving a real Pi session or subprocess).
- Behavior is asserted through the real boundary: tool results, command results, emitted events, persisted state, filesystem changes, exit status, cleanup. Not through internal helper calls.
- The extension under test is not mocked, and internal modules are not mocked to make setup easier.
- Every test owns its resources: temporary directories, sessions, subprocesses, listeners, env changes. Cleanup is registered immediately after acquiring a resource and runs on assertion failure too.
- Tests do not depend on another test having run first and leave no state that changes a later test.
- Every asynchronous dependency is awaited through an observable condition: `vi.waitFor`, `expect.poll`, an event, or a real readiness signal. No wall-clock `setTimeout` sleeps, no retries, no skipped tests, no raised timeouts to hide a race.
- Each test asserts one primary behavior and names it after that behavior.
- A process-owning extension proves loading alone starts nothing long-lived, and that shutdown cleanup is idempotent.

## Fences

- Do not edit `src/**`. If a test can only be made rule-compliant by changing production code, do not change it. Report the finding and the minimal production change you would make.
- Do not edit `extensions/pi-pstack/upstream/**` (immutable source) or `extensions/**/skills/poteto-mode/scripts/**` (bun tests, out of scope).
- Do not edit `.audit/**` or `extensions/scripts/**`.
- Do not edit files assigned to another auditor.
- Do not edit `extensions/AGENTS.md`.

## Never do this

- Never weaken, delete, or skip an assertion to make a change land.
- Never delete a test to silence a rule. Fix it or report it as unfixable with a reason.
- Never add retries, `test.skip`, `test.todo`, `.only`, global timeouts of `0`, or a longer timeout to hide flakiness.
- Never convert a test to a strictly weaker level (integration to unit, behavior to implementation) to make it simpler.
- Never add a comment that narrates the change or restates the code. Comments carry a non-obvious why only.
- Never reformat a file beyond the lines you change.

## Verification you must run

From the repository root, with the extension directory as the working directory for the suite commands:

1. `node extensions/scripts/check-vitest-conventions.mjs` must report `0 violations` (review notes are advisory).
2. From `extensions/<extension>`: `npx vitest run <your files>` must pass with every test it had before still present and passing.
3. From `extensions/<extension>`: `npm run typecheck` must pass when the extension defines it.
4. `node extensions/scripts/check-vitest-conventions.selftest.mjs` must still pass (do not edit the checker).

Run the focused file after each edit. Run your whole group at the end. Report the exact commands and their results.

## Report format

Return a concise report, no more than 60 lines.

- `files`: each assigned file, one line, with a verdict of `clean`, `fixed`, or `open`.
- `fixed`: bullet per change, one line each: `path:line  rule  what changed and why it is behavior-preserving`.
- `open`: bullet per finding you did not fix: `path:line  rule  evidence  the production change you would make`.
- `evidence`: the exact commands run and their observed results.
- `uncertain`: anything you could not decide, stated as a question.

Report only what you verified by running it. A claim you did not check is labeled as a guess.
