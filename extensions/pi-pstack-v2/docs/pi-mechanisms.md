# How pstack maps onto Pi

pstack 0.15.43 and cursor-team-kit 1.2.0 were written for Cursor. `upstream.lock.json` pins the exact upstream commit. This package keeps every skill, playbook, principle, agent, script, and guide chapter, and replaces each Cursor or Claude Code mechanism with the Pi mechanism that does the same job. The skills name Pi mechanisms directly. There is no adapter to read at run time.

Pi skips sub-agents, permission popups, plan mode, built-in to-dos, and background bash on purpose. Each row below names what pstack does instead.

## Pi's rules this port follows

| Pi rule | What pstack does |
| --- | --- |
| No sub-agents. Spawn Pi instances via tmux. | `pi_spawn` starts a separate `pi -p` process in its own tmux session with a standalone brief. It runs in parallel and wakes the spawning session with its report when it exits. |
| No permission popups. Run in a container. | Every `pi_spawn` and `tmux_run` job runs inside an isolated Linux container (Apple `container` on macOS, Podman or Docker on Linux) with a read-only root filesystem. Writes are limited to the worker's own session directory, its worktree or working directory, the repository's git directory, and private temp directories. Pi's own configuration stays read-only. No job runs uncontained. |
| No plan mode. Write plans to files. | A plan is a Markdown file, such as `plans/<slug>.md`. The human reviews the file. |
| No built-in to-dos. Use a TODO.md file. | Each checklist pstack used to keep in a todo tool lives in `TODO.md` at the root of the checkout you work in, as `- [ ]` and `- [x]` lines. It is working state, so never stage it. When the checkout already tracks a `TODO.md`, the checklist is `.pi/TODO.md`. |
| No background bash. Use tmux. Full observability, direct interaction. | Watchers, dev servers, long builds, and heartbeat ticks run through `tmux_run`. Nothing uses `&`, `nohup`, `setsid`, or `disown`. Every job is a tmux session you can attach to with the command `tmux_jobs` `list` prints. Its output shows there as it is written, and Ctrl-C there stops it. A job reads no input, so a command that needs an answer typed runs in the root session. |

Pi's design principle for customizing is to pick the least powerful mechanism that meets the need. Skills carry all workflow text. The one extension (`src/index.ts`) exists only for what a skill cannot do: start contained tmux jobs, wake the session when they exit, and put the model-role lines into the system prompt.

## Vocabulary

| Cursor or Claude Code | Pi |
| --- | --- |
| Subagent, `Task` call, delegate, worker | A Pi instance started with `pi_spawn`. Call it a worker, a spawned Pi, or by its role (explorer, reviewer, runner). Never call it a subagent. |
| `subagent_type: "poteto-agent"`, `"comment-sicko"`, `"ci-watcher"`, `"thermo-nuclear-code-quality-review"` | `pi_spawn` with `agent: "<name>"`. The role text comes from `agents/<name>.md`. |
| `subagent_type: generalPurpose`, `"shell"`, `"explore"` | `pi_spawn` with no `agent`. |
| `readonly: true` (Ask mode) | `pi_spawn` with `readonly: true`. The container denies writes outside the job directory and the edit and write tools are removed. MCP and shell stay available, so a reviewer that needs MCP can still be readonly. Here the network stays open, so readonly stops local writes only. A readonly worker can still change remote state with `gh`, `curl`, or an MCP tool, so the brief says what it must not change. |
| `readonly: false` (agent mode) | Leave `readonly` unset. |
| `environment: "cloud"`, Cursor cloud agent, `cloud_base_branch` | `pi_spawn` with `worktree: "<branch>"` and `base: "<ref>"`. The worker gets its own git worktree, and the container confines its writes there. Cursor cloud agents start from the repository's default branch. A worktree here starts from the session's current `HEAD` unless `base` names another ref, so pass the default branch as `base` to start from it. |
| `environment: "local"` | Omit `worktree`. |
| `run_in_background: true` | Nothing to set. Every `pi_spawn` runs in parallel, and you are woken when it exits. Keep working or end your turn. |
| Spawn N in one message | N `pi_spawn` calls in one message. |
| Nested subagents, launched by a subagent | pstack allows one level, which every pstack workflow fits. The root Pi and the workers it starts have `pi_spawn`. A worker started by another worker does not, and the root refuses a Pi request from one. Every worker keeps `tmux_run` and `tmux_jobs`. |
| `resume` an agent | `pi_spawn` with `resume: "<job id>"` continues that job's Pi session. |
| Steer or stop a running agent | `tmux_jobs` with `action: "stop"`, then a fresh `pi_spawn` with consolidated scope. A print-mode Pi takes no mid-run input. |
| Wait for agents | End your turn and let the wake arrive. `tmux_jobs` `wait` is for a short wait on named jobs. A spawned Pi running in print mode waits for its own jobs automatically before it finishes. |
| `file_attachments` | List the paths in the brief. |
| `model` slug such as `claude-opus-5-5-xhigh` or `grok-4.7-xhigh-fast` | `pi_spawn` `model: "<provider>/<id>"` and `thinking: "<level>"`. Thinking levels are `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`. Pi has no fast variant, so a "fast" choice is dropped. |
| `~/.cursor/rules/pstack-models.mdc`, `~/.claude/rules/pstack-models.md` | `~/.pi/agent/pstack-v2-models.md`, written by `/skill:setup-pstack`. The extension shows its role lines to the model in a `pstack-models` system-prompt section. A role with no line, or a line of `inherit-parent` or `auto`, runs on the session model, so omit `model`. |
| A model slug the Task tool rejects | A model `pi_spawn` rejects. It accepts only `provider/id` values that `pi --list-models` prints, which are the models Pi holds credentials for. Any other model fails at the call with the list of valid ones, before a job or worktree exists, and an omitted model runs on the session model. |
| Open a todolist, `TodoWrite` | Write `TODO.md`. |
| Custom Mode (Option+Enter on a slash skill) | `/pstack-mode <skill>`. The extension puts the skill in a `pstack-mode` system-prompt section every turn and records the choice on the session branch, so it survives `/compact`, resume, and `/tree`. `/pstack-mode off` ends it, and the footer shows the active mode. |
| `AskQuestion` (multiple-choice popup) | Ask in plain text with numbered options, then end your turn. Pi has no question popups. |
| `/loop` with an event | `tmux_run` the watcher command with `wake: "<what to do next>"`. |
| `/loop <interval>` heartbeat | `tmux_run` with `command: "sleep <seconds>"`, `wake: "<tick prompt>"`, and `repeat: true`. Stop it with `tmux_jobs` `stop`. |
| A shell command run in the background | `tmux_run`. |
| Plan mode, a plan to approve | A plan file. |
| `/<skill>` | `/skill:<skill>`. |
| A skill that says to run another skill by name | Pi hides skills marked `disable-model-invocation` from the skill list. The extension adds one system-prompt line giving the absolute path of the package's `skills/` directory. The model reads `<dir>/<name>/SKILL.md` and follows it. |
| `.cursor/skills/`, `~/.cursor/skills/` | `.pi/skills/`, `~/.pi/agent/skills/`, or the Agent Skills paths `.agents/skills/` and `~/.agents/skills/`. |
| `.cursor/rules/*.mdc`, always-applied rules | `AGENTS.md` (project) or `~/.pi/agent/AGENTS.md` (user). |
| `~/.cursor/plugins/`, `.cursor-plugin/plugin.json`, `/add-plugin` | A Pi package: `pi install <source>`, listed by `pi list`. |
| Cursor chat transcripts in `~/.cursor/projects/<slug>/agent-transcripts/` | Pi sessions in `~/.pi/agent/sessions/--<cwd with / as ->--/*.jsonl`. Spawned workers keep theirs in `~/.pi/agent/pstack-v2/jobs/<id>/session/`. The extension names the current session's file in a `pstack-session` system-prompt section, and a brief that asks a worker to read it carries that path, because a worker's agent directory is its job's own. |
| `/create-skill` | Write `SKILL.md` to Pi's skills spec (Agent Skills format) and check it loads with `/skill:<name>`. |
| Cursor Automations, routines, webhook wakes, `SendToUser` | A tmux job that runs `pi -p` against a session, or Pi's RPC mode. Secrets come from environment variables the user sets, never from chat. Upstream's dormant benny pack (Slack issue triage, then reproduce-and-fix) runs only on that service, so this package does not ship it. |
| Cursor canvas | A self-contained HTML file opened in the browser. |
| Cursor Bugbot, agentic security review | Unchanged. They are GitHub reviewers whose comments any harness reads from the forge. |
| Cursor's built-in PR tool | `gh`. |
| MCP tools | Pi's built-in MCP (`pi mcp list`, `~/.pi/agent/mcp.json`, `.pi/mcp.json`) and Codemode (`"defaultTools": ["+codemode"]` in settings). Workers get a copy of your settings, so they have the same MCP servers and Codemode. |
| Cursor's agent store, project store, project tracker | Files in the checkout: `decisions.tsv` and `plans/`. A worker keeps its `decisions.tsv` in its worktree, which the root reads at `<agent dir>/pstack-v2/jobs/<id>/worktree/`. |
| Orchestrate's `notes.md` | A file at the checkout root, never staged, like `TODO.md`. |
| Origin (`origin pr`) | Kept as is when `command -v origin` succeeds and Origin resolves the repository, otherwise `gh`. Graphite is never required. |
| Hold or stand-down order to running agents | `tmux_jobs` `stop` after each worker commits a `wip:` checkpoint, then a fresh `pi_spawn` to release. |
| A lane that needs a simulator, `open`, a local display or socket, or auth that exists only on this machine | Run it in the root session, which is not contained. |

## Container details

- Every job runs in one Linux container: Apple `container` on macOS, Podman (first) or Docker (if `docker info` works) on Linux and WSL2. Native Windows is unsupported. With no runtime, `pi_spawn` and `tmux_run` refuse to start with install steps. There is no other isolator to fall back to.
- The container has a read-only root filesystem, no capabilities, an empty `/run`, a private tmpfs `/tmp`, and no runtime socket, so a job can neither start a container nor reach tmux, the session bus, or any other host service. It runs as your uid, with half your CPUs and 8 GiB of memory.
- Mounts are directories only, each at its own host path so absolute paths in worktrees and Pi's symlinks keep working. A job gets its working directory or worktree and that checkout's git directory read-write, and for Pi workers its own `session/` and `nested/` directories and private temp directory. The Pi install, the pstack package, and your agent directory are read-only. Your `$HOME` is never mounted. Apple `container` cannot mount a single file, so every runtime gets the same directory-only policy.
- The image is `pstack-v2-job:<hash of container/Containerfile>`. `ensureImage` builds it once on first use, so the first job can take minutes, and later jobs only pay VM boot. It carries `node`, `git`, `rg`, `gh`, `jq`, `python3`, and a C toolchain. It holds no Pi, pstack, or credentials, because Pi runs from the read-only mount of your own install. Set `PSTACK_V2_IMAGE` to use another image, which pstack checks and never builds. Jobs set `PSTACK_V2_CONTAINED=1`.
- Host-only toolchains do not exist in the guest, which is Linux. Xcode, simulators, `open`, and local displays work only in the root session, which is not contained.
- A job cannot add or change a git worktree or submodule, apart from the metadata of the worktree it works in, and cannot write the git directory of a nested repository. A job that needs another revision beside its own exports it into its private temp directory with `git archive <sha> | tar -x -C "$TMPDIR/<name>"`.
- Before a job starts, the root creates any missing `hooks/`, `info/`, `worktrees/`, and `modules/` directory in the git directory, empty, so they can be mounted read-only. Git reads them as nothing.
- Each job's `TMPDIR`, `XDG_CACHE_HOME`, and npm, bun, pip, uv, Go, Yarn, and Deno caches point at its private temp directory, so installs and builds still work. Those caches are deleted when the job exits, and the rest of its temp directory is kept for the report. A command a worker starts shares the worker's temp directory.
- `cwd` must be inside the session's project, which is the git top level or else the session cwd, or a linked worktree of the same repository. A checkout of another repository is refused even when it sits inside the project, since the job would be handed that repository's git directory. No writable path may contain Pi's agent directory. The model cannot widen its own container by naming another directory.
- Paths something outside the container later executes from stay read-only even inside a writable checkout. Directories are mounted read-only over the writable checkout: the git `hooks/`, `info/`, `worktrees/`, and `modules/`, the code entries of every `.pi` directory (`extensions`, `npm`, `git`), and `.vscode` and `.idea`, plus the `.cursor` and `.claude` entries apart from their instruction directories `rules`, `commands`, `worktrees`, `skills`, and `agents`, which a job may still write.
- Files cannot be mounted, so they are guarded instead (`guardFiles`): git `config` and `config.worktree`, `.git` pointer files, `.pi/settings.json`, `.pi/mcp.json`, `*.code-workspace`, and `.cursorignore`. At launch the root hashes and copies each one. When the job exits or is stopped, the host wrapper restores any that changed or vanished and moves the job's modified copy into the job's `quarantine/` directory. The same sweep moves any new `.pi` code entry, editor or harness entry, or `.git` entry the job created into `quarantine/`, and the job's output says so. The sweep never follows a link, and a `.pi` symlink you already had is left alone. Moving, not deleting, keeps a file you created yourself during the job recoverable.
- Jobs never write your Pi agent directory, your `auth.json` included. Each top-level job gets its own agent directory, through Pi's `PI_CODING_AGENT_DIR`, shared by every job it starts. It links to your configuration, holds `settings.json` with its local package paths anchored to your real agent directory, and links `auth.json` into a shared credentials directory, the one shared writable mount, which holds a copy of your credentials and Pi's locks. No job can change what another job's Pi loads.
- Pi runs an `auth.json` key that starts with `!` as a command, so the credentials copy holds no command. For a worker's own provider, the root resolves the command once when it starts the worker and puts the resulting key in the copy. Every two seconds, and once more after a job ends, the root carries refreshed OAuth tokens between your `auth.json` and each copy, the later expiry winning, under Pi's lock on both. Only OAuth tokens move, so nothing a job writes as a key or a command reaches your `auth.json`, and a provider you logged out of is never brought back.
- When a job exits, its wrapper runs `stop` on the container, then `kill` if it does not stop, before cleanup, so no child it left behind acts after cleanup. `tmux_jobs` `stop` and root shutdown stop any leftover container labelled with the session.
- Nested jobs are still brokered on the host, because a worker holds no container runtime. A Pi worker's own jobs get their own container, so `readonly` holds at any depth, and a resumed worker keeps its `readonly`. A worker writes the job as a request in its `nested/` directory, and the root Pi launches it under mounts built from the paths it validated. The root refuses any request that would write, or run, outside what it granted the top-level worker, so no worker can hand a descendant more than it was given. The root writes results only under the top-level job, never into a worker's directory, and serves requests while it runs. A worker's container keeps `.git/worktrees` read-only, so when a worker passes `worktree` to `pi_spawn`, its request carries the branch and base, and the root creates the worktree from the worker's own checkout before it launches the job. The checkout lands in the job's results directory, `<top-level job>/brokered/<hash>/worktree`, which no worker can write, so no worker can swap in a link for git to check out through. The root creates it only for a worker that may write the repository and only at that path, computes the checkout's protected paths itself, keeps a `readonly` job read-only, creates nothing for a request it refuses, and removes the worktree and any branch it created when it cannot launch the job. If you quit the root Pi, nested requests wait until you resume that session.
- The main session is not contained. To contain it too, run Pi as Pi's own guide to isolated environments describes. pstack ships no launcher for that.

## What the container does not cover

- Reads and network access stay open, so a job can read anything mounted and send it over the network. Only the mounted directories are visible, not your `$HOME`.
- A writer job's changes are code you and the root Pi later run, such as tests, builds, package scripts, Makefiles, `.envrc`, a nested repository with its own `.git`, and instruction files such as `AGENTS.md` and `.pi/skills`. Review a worker's diff before you run or trust it, as with any agent.
- A worker can use a provider whose credential is a `!command` only when that provider is its own model's, since the root resolves only that one. Set a key or log in with OAuth for any other provider a worker needs.
- A job can create a `.pi` code entry, an editor or harness entry, or a `.git` entry where none existed at launch, or edit a guarded file, because a parent directory cannot be locked and a file cannot be mounted. The sweep moves or restores them when the job ends.
- A job can leave a fake rebase in progress in the git directory, whose steps run if you then run `git rebase --continue`.
- A print-mode run waits for every job it started with a wake message, so one that never exits keeps it running.
- A bash here-document can fail in a checkout the job cannot write, such as a readonly worker's, so the job changes to `$TMPDIR` first or writes with `printf`.
- Cargo and Maven caches are not redirected to the job's private temp directory, so their downloads fail inside a job.
- Until a job exits, a guarded file it modified or a protected path it created still exists, and a process started outside the container in that checkout during the job could use it. That includes a changed `.git/config`.
- A job can hold the lock on its credentials copy, which pauses token sync for that job until it ends.
- A job's agent directory is read-only apart from its credentials copy and locks, so Pi state a worker would write there does not persist from a worker. That covers an MCP OAuth refresh in `mcp-auth.json`, a model catalog refresh, and package installs. An OAuth MCP server may need a login from the root session first, since a worker cannot save a refreshed token.

## Jobs on disk

Each job lives in `~/.pi/agent/pstack-v2/jobs/<id>/`: `job.json` (the spec), `brief.md`, `wrapper.sh`, `inventory.json`, `output.log`, `exit`, its private `tmp/`, a top-level job's `agent/`, any `quarantine/`, and for Pi workers `session/`, `nested/`, and `stderr.log`. The job directory is read-only to the job, so a job cannot rewrite its own spec or exit code. The host tmux wrapper writes `output.log` and `exit`. A Pi worker can write only `session/` and `nested/`, and the jobs it starts live in `nested/`. Each spawning session runs its own tmux server on a socket in `/tmp/pstack-v2-<uid>/`, named from a hash of the session id. `tmux_jobs` `list` prints a `tail -f` command to follow each job's output and a `tmux attach` command for each running job. A worker's report is every answer it completed, read from its session file, so a reply to a late job notice cannot replace it. A wake is claimed once through a `woken` marker file, so restarting Pi never delivers a report twice.
