# Replay benchmark, 2026-11-15

> Historical run. [`final.md`](final.md) is the later recorded run, not a description of the current package. The numbers below describe the package as it was on that date.
>
> The commands below use the script names from that date: `report.py`, `profile-summary.py`, and `visual/mockup-fixture.py`. They are now `report.ts`, `profile-summary.ts`, and `visual/mockup-fixture.ts`, run with `node`. `run.py` is unchanged.

## Verdict

The full extension uses less CPU than stock Pi on the replay workload: 185 ms against 262 ms of workload CPU (medians of 7 runs, set B, ranges 161..194 and 236..292). Full was lower than stock in all 14 paired rounds. The theme alone shows no measurable difference from stock. Neither configuration shows a measurable difference in idle CPU, echo latency, echo misses, event-loop delay p99, or idle terminal output.

## Setup

- Machine: Apple M4, 10 cores. `sysctl -n machdep.cpu.brand_string` prints the model.
- Pi 1.5.2 on Node v26.13.1.

**Event-loop delay p50.** Every sample includes the 10 ms sampling interval. An idle loop reads 11.0 ms in all three configurations, which is the timer's own slack. Stock reads 10.8 ms during the workload because extra wakeups let the sampler's timer fire closer to on time. Full reads 11.0 ms, the same as an idle loop. After the first second of idle, 41 of 42 runs wrote nothing. One `full` run in set B wrote 4 bytes after the first second. That did not recur in 14 further `full` runs with `--keep-artifacts`, so the bytes and their cause are unknown.

**Limiter.** Pi's own render path bounds the workload in both configurations. `doRender` takes 87 ms inclusive in `full` and 118 ms in `stock`, and the Markdown lexer for the streaming message takes 34 to 38 ms of that. Timers come next (`processTimers`, 25 to 28 ms self). Those are the bench provider's 8 ms delta timer and the 10 ms event-loop sampler, which both configurations share.

**Why full uses less CPU.** Two stock components that `full` replaces account for the gap:

- Stock's streaming `bash` preview (`VisualLinePreview.render` and `truncateToVisualLines`) takes 24.9 ms inclusive. In `full`, the compact row's `render` (`row.ts`) takes 9.6 ms inclusive for all four tool rows.
- Stock's built-in footer `render` takes 15.1 ms inclusive, including `formatCwdForFooter`. The cached `full` footer takes no samples.

Busy JavaScript time differs by 33 ms (244 against 211 ms), and `(program)` and GC add another 9 ms. Together that covers about 42 ms of the 60 ms CPU gap between the two profiled runs. The rest is likely time on V8 and libuv helper threads, which `process.cpuUsage()` counts and a main-thread profile does not. That part is an inference.

**pi-snoop-tui share.** Functions in `pi-snoop-tui/src/` take 1.3 ms self time, 0.6% of busy time, all of it in `row.ts` `render`. No footer or chrome function appears.

### What the bytes show

Pi 1.5.2 draws in the alternate screen and writes only the visible 40 rows, so every step but exit writes 0.6 to 13 KB in every configuration. On exit Pi prints the whole transcript to the normal screen: 1.40 MB for stock and 0.48 MB for full, because compact rows are shorter. Settle times are therefore bound by rendering the component tree, not by terminal output.

### Limiter

One extra unreported run of `stock` and `full` ran with `NODE_OPTIONS="--cpu-prof"`. `python3 profile-summary.py <dir>` without `--record` covers the whole process.

- Full spends 334 ms self time in Pi's `truncateToWidth`, against 6.5 ms in stock. Of that, 239 ms comes from `Panel.render` in `src/rows/row.ts` (the `map` at line 226) and 96 ms from `RowHeader.render` (line 139).
- Bucketing the full profile by 100 ms puts the expand step at about 0.5 s of busy time, and 375 ms of it falls under `Panel.render`. The paired expand gap is 312 ms, so `Panel.render` covers it.
- `Panel.render` has no cache. Each render passes every line of every expanded panel through `truncateToWidth`, after `Box` has already rendered and padded it. Expanding all 1050 rows makes every one of those panels render in the same frame.
- `RowHeader.render` misses its cache when the width or view changes, so it costs about 50 ms at startup and 15 to 30 ms per resize. Stock pays similar costs in its own components, so those steps show no loss.
- Inference at the time: while rows stay expanded, later frames repeat the `Panel.render` truncation. The panel cache experiment below measures this path.
