## Rules

1. You own only the files your package lists. Never edit a clause file, `AUDIT.md`, `scripts/check-native-parity.mjs`, `scripts/parity-contracts.mjs`, or a file another package owns. If a fix needs a file you do not own, list it under HANDOFF in your report with the exact change.
2. Test first. Write the failing test, run it, see it fail for the stated reason, then fix, then see it pass. New tests go in new files named in your package. Do not edit existing tests unless a change you made legitimately invalidates one, and name each such edit in your report.
3. A gap is closed only when a test or generated artifact a stranger can rerun shows the behavior. Prose that restates the requirement does not close it. If upstream behavior is a defect and the reference calls it a defect, fix it natively rather than copying it.
4. Do not edit generated files under `skills/` or `prompts/` by hand. Change `scripts/resources.mjs` or a `scripts/overlays/*.mjs` overlay, then run `bun run generate`. Run `node scripts/resources.mjs` to confirm no drift.
5. Run only narrow tests (`npx vitest run test/<file>` and `bun test ./test/helpers/<file>`). Five other workers share this machine, and a full run under load produces timing flakes. The coordinator runs the full suite at the end.
6. `scripts/structure` limits apply to every file you write: under 800 lines per file, under 50 lines per function, at most four nesting levels, and no `console.log`. `test/structure.test.ts` enforces them. Match the surrounding code's style and comment density.
7. Do not commit. Do not claim a gap closed that you did not prove. A gap you cannot close stays open with a one-line reason in your report.
8. Helper defect fixes to the shipped scripts under `skills/poteto-mode/scripts/` are overlays. Add `scripts/overlays/<name>.mjs` (see `scripts/overlays/README.md`), regenerate, and put the bun test in `test/helpers/<name>.test.ts`. Import the shipped file by relative path from `test/helpers/`. The gate runs these tests with `"runner": "bun"`.

## Placement decision for cloud

The reference says Shipping verifiers, autopilot owners, swarm workers, and plan live lanes run as `environment: "cloud"` agents unless a task needs this machine. In this package `environment: "cloud"` runs on a configured separate VM with no local fallback in the Task tool itself. Playbook text restores the upstream default: use `environment: "cloud"` when the host contract shows a configured remote executor. When none is configured, run the unit locally, say so, and record the fallback in the decision log and the reply. Local-only exceptions stay as upstream lists them. The Task tool never falls back silently.
