## Identifiers

`RunId` and `WorkerId` match `^[a-z0-9][a-z0-9-]{0,39}$`. Validate at every boundary.

tmux uses its own server: always `tmux -L pstack`. Session name `pstack_<runId>_<workerId>_<hash>`, where `<hash>` is the first 8 hex digits of sha256 of `<project>\0<runId>\0<workerId>`. Ids never contain `_`, so the parts cannot run together, and the hash keeps two projects apart on the one server. When the host does not answer, abort ends the session only when the identity recorded in `claim/tmux.json` still matches (see Runtime invariants); otherwise it reports `refused` and leaves the session running. Never call `kill-server` outside tests. Tests use `-L pstack-test-<random>` and may kill only that server.

## Run files (spec 7)

Run root: `<project>/.pi/pstack/runs/<runId>/`. `<project>` is the git toplevel of the parent's cwd, or the cwd outside git.

```
run.json            { schemaVersion: 1, runId, title, playbook, upstreamRevision, createdAt, parentSessionFile|null, inputCommit|null }   // null: an automation run, owned by its automation adapter, not a chat
TODO.md             parent is the sole writer
decisions.tsv       show-me-your-work format: ts, phase, decision, why, evidence, result
events.jsonl        append-only; extension and hosts append { ts, runId, workerId?, kind, data }
workers/<workerId>/
  assignment.json   immutable after creation (schema below)
  brief.md          the worker's self-contained brief, written by the parent
  claim/            created exclusively (mkdir) by the parent at spawn; its presence forbids a second spawn
    identity.json   created exclusively by the host with its digest, instance, pid, and process start time; a second host for the assignment fails here
    launch-env.json written 0600 and exclusively by the parent; read once and unlinked by the host before Pi starts
    tmux.json       written exclusively by the parent from `new-session -P`; the session identity abort's fallback checks
  control.sock      host control socket, mode 0600 (if the path exceeds 100 bytes, the host uses /tmp/pstack-<uid>/<sha256(runDir)[0..16]>-<workerId>.sock and records it in state.json)
  state.json        host-written snapshot; never a liveness oracle
  report.md         written by the worker
  evidence/         receipts written by the worker
  worktree/         git worktree for writable workers
verification/receipts/<id>.json   one file per receipt, created with O_EXCL; no shared file, no lock. The verdict list is derived by reading the directory. Recording needs a filesystem with hard links under the run root; `ENOTSUP`, `EPERM`, `EXDEV`, or `EMLINK` from the link fails recording with an error naming that requirement, and nothing is recorded.
```

Write JSON atomically (temp file plus rename). Plans live in `<project>/.pi/pstack/plans/<slug>.md`.

## Assignment (`assignment.json`)

```ts
{
  schemaVersion: 1,
  runId: RunId,
  workerId: WorkerId,
  kind: 'pi' | 'watch',
  role: 'poteto' | 'explorer' | 'investigator' | 'candidate' | 'judge' | 'verifier' | 'reviewer' | 'owner' | 'watcher' | 'comment-sicko' | 'general',
  brief: 'brief.md',                 // relative to the worker dir; kind 'pi' only
  model: 'inherit-parent' | '<provider>/<id>',
  thinkingLevel: 'off'|'minimal'|'low'|'medium'|'high'|'xhigh'|'max' | null,
  workspace: { mode: 'worktree', inputCommit: string }   // writable: extension creates worktree/ at inputCommit
           | { mode: 'readonly', path: string }           // absolute; tools: read,grep,find,ls,bash_readonly,pstack_evidence (+MCP per capabilities)
           | { mode: 'container', inputCommit: string },  // writable clone of the pushed remote at inputCommit, inside the container .pi/environment.json configures (see Container workers)
  skills: string[],                  // skill names the brief requires the worker to read first
  watch?: { argv: string[], cwd: string }   // kind 'watch': argv runs in tmux; exit wakes the parent
}
```

Optional with defaults: `schemaVersion` 1, `kind` 'pi', `skills` [], `thinkingLevel` null, `capabilities` the run's default (see Capability boundary), readonly `workspace.path` and `watch.cwd` the project root, `<runRoot>/../../../..`. `parseAssignment(raw, { capabilities, projectRoot })` fills them in, so parsing a parsed assignment returns it unchanged; `loadAssignment` supplies both defaults from the run root and its `run.json`. `spawnAssignment` writes the parsed assignment back to `assignment.json` as `JSON.stringify(assignment, null, 2)` plus a newline, by temp file and rename, only while `claim/` is absent and only when the file's text differs, then reloads it and creates `claim/`. The claim therefore protects the complete file, and the digest the host and the parent agree on is that file's. Every spawner writes the same bytes, so a spawner that races another to the claim changes nothing. A claimed file is never rewritten. `generated/skills/poteto-mode/references/worker-assignment.md` holds one complete example per workspace mode and kind, and a test parses every example with the real parser, both as written and with every defaulted field left out.

`role` selects a role instruction document from `generated/agents/<role>.md` (U03 produces `poteto.md` and `comment-sicko.md` from upstream agents; other roles use `general.md`).

## Tools (spec 8.4)

Exactly two model-facing tools, TypeBox-validated.

`pstack_worker`:

- `{ action: 'spawn', runId, assignmentPath }`. Validates the assignment and its path (must be `<runRoot>/workers/<workerId>/assignment.json`). Resolves the model. Starts `tmux -L pstack new-session -d -s <session name> -- node <pkg>/dist-or-src/worker-host entry <assignment>`. The host creates the worktree after it takes `claim/`, so only the claim holder creates it. It creates a new branch `pstack-run/<runId>/<workerId>` at `inputCommit`. An existing `worktree/` path, or an existing branch of that name, fails the host; nothing is reused. Waits for the host handshake. Sends the brief as the first prompt. Returns `{ workerId, tmuxSession, attach: 'tmux -L pstack attach -t <session>', sessionFile, model }` once the host answers, without waiting for the work. When tmux's answer about the launch is lost, spawn first waits up to the start-check window (see Runtime invariants, spawn outcome), and the tool description says so. Refuses when `claim/` exists.
  Every worker starts through `spawnAssignment(project, runId, assignmentPath, options)` in `src/workers.ts`, the only code that runs `tmux new-session`: this action (after its owner check) and the automation adapters (`spawnInTmux` in `src/automation/dispatch.ts`, the default `spawnWorker` of Benny and webhook routines). An automation run has no parent session, so it runs `pi` from PATH, and `inherit-parent` launches Pi with its configured default model.
- `{ action: 'inspect', workerId, runId }`. Live host state, or `unavailable` with reason.
- `{ action: 'steer', workerId, runId, message }`. RPC `prompt` with `streamingBehavior: 'steer'`: it joins the active run, or starts one when Pi is idle. RPC `steer` sent as a run ends would queue behind a run that never starts.
- `{ action: 'abort', workerId, runId }`. clear_queue, abort, then orderly shutdown of that host only. When the host does not answer and `claim/` holds no `identity.json`, a spawn may have died between taking the claim and starting tmux: abort waits the bounded start check. With no claim by a host and no session by the worker's name, the worker is `abandoned`: abort appends an `abandoned` event to `events.jsonl`, unlinks `claim/launch-env.json`, and leaves `claim/` in place so the assignment is never spawned again. The retry is a fresh worker id. A session by that name without a host claim is refused and left running.
- `{ action: 'collect', workerId, runId }`. Final state, `report.md`, final assistant text from the native session file, evidence file list. A worker that is not settled returns its live state, never a result. Settled means the latest settle covers the latest work generation: the host counts each prompt, steer, or follow-up it forwards as a generation and persists it in `state.json` before forwarding. A run's settle covers the generations acknowledged before the `get_state` answer that found Pi quiescent (see Runtime invariants), and the host ending covers all of them. A host that is gone with a generation no settle covers returns no result.

`pstack_evidence`:

- `{ action: 'record', runId, receiptPath }`. Validates a receipt under the run root and stores it as `verification/receipts/<id>.json`: the recorder writes a private temporary file and hard-links it to that name, so the name never holds a partial receipt and concurrent recorders share no file and take no lock. Recording an id that exists is idempotent when the receipt is identical (deep equality of the receipt object) and an error when it differs. `verify` and `list` read the directory.
- `{ action: 'verify', runId, target }`. Re-checks every receipt for `target` (a TODO step id, worker id, or commit): files exist, sha256 match, `commit` equals the target commit when given. Returns `pass`, `fail`, or `inconclusive`. A missing receipt is `inconclusive`, never `pass`.
- `{ action: 'list', runId }`.

Receipt:

```ts
{ schemaVersion: 1, id: string, runId: RunId, target: string, kind: 'test'|'command'|'screenshot'|'trace'|'review'|'measurement'|'other',
  verdict: 'pass'|'fail'|'inconclusive', commit: string|null, environment: string,
  command?: string[], exitCode?: number, artifacts: { path: string, sha256: string }[], defects?: string[], reason?: string, createdAt: string }
```

## Wakeups (spec 9.1, 11.3)

While a parent session is live, the extension watches its run's hosts. When a worker settles (idle after work, failed, aborted, unavailable) or a `watch` worker exits, it posts one `pi.sendMessage({ customType: 'pstack-worker', content, display: true }, { triggerTurn: true, deliverAs: 'followUp' })` per transition, with `details: { transitionId, runId, workerId, phase }` where `transitionId = <workerId>:<host instance>:<settle sequence>`. The parent session file is the delivery record: Pi persists each `sendMessage` as a `custom_message` entry with its `details` (docs/session-format.md; observed for `pstack/shell`). Before sending, and on every reconcile, the extension scans the active branch, `ctx.sessionManager.getBranch()` (root to current leaf), for `custom_message` entries of type `pstack-worker` and sends only transitions whose id is absent. Delivery is defined against the active branch: after `/tree` moves the leaf above a wake, the parent model no longer sees it, so it is sent again on the new branch. The in-memory record of wakes handed to Pi but not yet persisted is cleared on every `session_start` and `session_tree`.

Fork policy: a run's owner is the session file in its `run.json`, and a fork or clone does not change it. The forked session has a new file, so it gets no wakes and cannot control the run's workers. The original session gets them when it is reopened. To hand a run to a fork, the parent writes a new run. `events.jsonl` logs the attempt for audit only and is not consulted for delivery. The host keeps every settle in `state.json`, so a settle is never dropped before a parent sees it. At 10,000 settles the host refuses new work with an error instead of dropping one. The extension marks a wake sent only after `sendMessage` returns, so a throw leaves it for the next poll. On `session_start` the extension reconciles `run.json` files whose `parentSessionFile` matches, against `tmux -L pstack list-sessions`. A missing session with no settled state is reported `unavailable`, never complete.

## Extension surface (spec 8, U04c-1)

`src/extension.ts` is the package's one extension. With `PSTACK_WORKER=1` it calls only `registerWorkerSideTools(pi, process.env)`. Otherwise it registers `pstack_worker` (through `registerWorkerTools` with the resolver below), `pstack_evidence`, the persistent style, slash routing, and `/pstack`. No other model-facing tool and no other command.

Model resolver. `pstack_worker` spawn resolves an assignment's `model` with `resolveRole` from `src/models.ts` and `~/.pi/agent/pstack/models.json`: the spec stands in as the line of a single-model role, so it gets the role fallback and level clamping. `inherit-parent` with `thinkingLevel: null` is the session's model and level; with a level, the session's model at that level, clamped. A named model with `thinkingLevel: null` keeps its default level (the worker gets `null`); it is matched at `off`, or at the budget level when it cannot turn thinking off. No match is a spawn error naming the limitations. An invalid `models.json` fails the spawn.

Persistent style (spec 8.3). `/pstack on` and `/pstack off` append a custom entry `pstack/style` with `{ on: boolean }`; the last one on the active branch is the state, so resume, fork, and reload restore it. On a run with `messageType: 'user'` only, `before_agent_start` adds one `custom_message` of type `pstack-style`, `display: false`: with the style on, the loaded `poteto-mode` skill block (`details.kind: 'skill'`) when the compaction-aware context (`buildContextEntries()`) holds no `pstack-style` skill message after the last off notice; with the style off and that skill still in context, one notice to stop following it (`details.kind: 'off'`). A later task, a wake turn, or a compaction that kept the skill adds nothing; a compaction that summarized it away brings it back once.

Automation sources (spec 14.1). An event source runs as a `kind: 'watch'` worker through `spawnAssignment`, never a tmux call of its own. Run id `serve-<first 12 hex of sha256(name)>`, title `Automation <name> event source`, `parentSessionFile` the starting session (its wake watcher hears the source exit). Each start is a fresh worker `source-<n>` with role `watcher`, readonly workspace and `watch.cwd` at the project. `<name>` is a routine when `<project>/.pi/pstack/automation/<name>/config.json` has `kind: 'routine'`, whose argv is `node <pkg>/scripts/routine-setup.mjs --project <project> --name <name> --serve` (default port 47913). Otherwise it is the Benny automation whose `automations.<kind>_name` in `.pi/benny/configuration.yaml` is `<name>`, whose argv is `node <pkg>/scripts/automation-serve.mjs --project <project> --kind triage|reproduce` (any free port unless `--port`). That entry (built to `dist/automation-serve.js` from `src/automation/serve-cli.ts`) loads the config with `loadBennyConfig`, reads the Slack connector token from `~/.pi/agent/pstack/credentials/slack.json` field `token` (missing or not 0600: it exits, failing closed), and runs `startEventSource` with the webhook source keyed by `credentials/<name>.json`. It wires `src/automation/wiring.ts`: the tracker adapter for `tracker.type`, the trusted tracker policy, and the prerequisite probes, then starts the settler (below). A case whose prerequisite does not hold is logged `blocked`. Both entries print a JSON line with `url`, which `status` reads from the pane.

Benny completion (spec 14). The serve process is a plain Node process and receives no Pi wake, so `src/automation/settle.ts` polls (`--settle-poll-ms`, default 5000). Which runs still owe a reply comes from the event log alone: `automation.pendingRuns()` is every `dispatched` entry without a `completed` entry, and `complete(runId, result)` appends `completed` after it enqueues the outbox actions and flushes them, so a restart, or a crash anywhere in between, never completes a run twice: the outbox ids are one per purpose, and a tracker action already queued skips the policy. `collectRun` applies the `collect` rule from Tools: the latest settle covers the latest generation on an idle or ended host, read from the host's control socket (`inspectHost`) and else from `state.json`. A host that ended, or whose process is gone, holding work no settle covers is a failure. The worker's final assistant text is a JSON object `{ text, tracker? }` or plain text. A settle of `failed`, `aborted`, or `exited`, a failure above, an empty final message, or a reply with no single verdict marker completes with the failure reply (triage: `[benny:other]`, which repro never trusts). A tracker intent the parent refuses is dropped and the verdict still posts.

Pack provenance. `generated/automations/benny` is compiled from the untouched `vendor/upstream-pstack/automations/benny` by `scripts/compile-skills.mjs` through the recorded rules in `adapters/benny-pack.ts`, with the same manifest, drift failure, and residual-primitive check as the skills. `check-parity` reports a hand edit. There is no hand-kept copy.

Outbox, retries, and deadlines. Each outbox entry is performed alone: an entry that throws is logged (`outbox-failed`), backs off 5 s doubling to 60 s, and after `OUTBOX_RETRY_LIMIT` (5) attempts is `failed`, so one failing entry never blocks another. A restart retries pending entries at once. `complete` holds the reply only while the tracker entry is pending. A tracker entry that failed makes the reply the failure reply (`[benny:other]`, so repro never starts). A reply goes only under a thread parent that is still there, and it is read back as a reply under that thread before it is acknowledged. A reply that fails its retries closes the issue this run created through the tracker's compensation action (`operation: close`, marker-reconciled like any write) and logs `compensated` with `verified`. The settler also aborts a run that never settled when `budgets.triage_total_minutes` (triage) or `budgets.repro_minutes` (repro) passes after its `dispatched` entry, through the host's `shutdown` (the `pstack_worker abort` path). That covers a claim with no `state.json`, a live idle host, and a live running host. The abort outcome is logged (`deadline`) and the case completes with the failure reply. The abort is `abortWorker` (exported from `src/workers.ts`, what `pstack_worker abort` runs) through `abortInTmux` in `src/automation/abort.ts`, so a host that does not answer is stopped by ending its claimed tmux session, and a claim no host took is abandoned (launch secrets removed, `abandoned` event, claim kept), the same verified path. The logged outcome is the receipt's disposition (`stopped`, `session-ended`, `abandoned`, or `refused: <why>`).

Proof before a repro outcome (vendor reproduce SKILL.md:25, 126-134 'must appear twice through real UI'; SKILL.md:218-225 and references/verify-existing-fix.md; FOR_AGENTS.md:19). The parent cannot see a real UI, so it requires what a worker that did the work leaves behind: `repro.json` in the run's artifact folder, `{ reproductions: [{ at, artifact, state }], existingFix?: { url, outcome, baseline: [...], patched: [...] } }`, described in the brief. `src/automation/proof.ts` counts a set of runs only when at least two have a parseable `at` after the case or turn began (and at most 60 s ahead of the parent's clock), a non-empty `state`, and an artifact that is a regular screenshot, recording or note (the evidence types) inside the run's folder, written during the case, with strictly increasing times and different bytes. `src/automation/accept.ts` applies it to the worker's reported outcome in `complete`: `Reproduced` needs two reproductions (or, with an `existingFix` section, an `insufficient` verification); `Verifying existing fix` needs a `github.com` pull or commit link, outcome `confirmed`, a baseline measured twice and a patched build measured twice after it. A failed check is not trusted: `Reproduced` is recorded as `Could not reproduce` (upstream: 'the repro is not confirmed ... use Could not reproduce') and `Verifying existing fix` as `Blocked` (upstream: inconclusive, state which half could not be measured), the worker's source text and evidence are dropped, the operations thread says why, and `repro-outcome` logs `unverified`. A correction (`corrected: true`) or a rerun that still says `Reproduced` owes two observations made since its turn began. A verified existing fix (`existingFix` in `repro-outcome`) holds no rejection window and gets no fix turn (SKILL.md:232 'No existing fix artifact appeared'). What stays unproven, and is the remaining coverage gap, is that the captures came from a real UI and show the symptom, and that a fix artifact existed at all.

Draft-only pull requests (vendor reproduce SKILL.md:291 'Open a draft pull request. Never merge or deploy', configuration `repository.draft_only: true`). A repro worker runs as the operator in a worktree, so it holds the operator's `gh` and git credentials and no tool boundary removes them (same-uid limit, Runtime invariants). Prevention is by construction. The fix turn tells the worker to commit on its run branch `pstack-run/<runId>/owner` and return `pullRequest: { title, body }`, and not to push or open anything. `src/automation/pull-request.ts` (`landFix`) then acts only on state it reads: the run branch has commits beyond the input commit, the worker's record shows `fix.patched` measured twice since the fix turn began, and a title and body exist. `src/automation/forge.ts` (`openDraft`) pushes only `refs/heads/<run branch>` and only when the worktree's `remote.origin.url` is the `repository.url` repository, then runs `gh pr create --draft --base <repository.default_branch> --head <run branch>` with the action marker `<!-- pstack-action:<id> -->` in the body, finds a pull request a crash left by its head branch instead of creating a second, and reads the result back, converting it with `gh pr ready --undo` if it is not a draft. The operations status `Draft pull request opened` and its link are the parent's, set only after that read-back; a worker's own claim of it is not believed. Anything that fails closed reports `Fix did not land` with the reason: no commit, no patched proof, no pull request text, a `repository.url` that is not github.com, a failed push or `gh` call after 5 attempts a minute apart. Detection is the backstop for a worker that goes around this: `src/automation/fix-guard.ts` lists the pull requests of the run branch (`gh pr list --head`, at most once a minute per run) and converts every open non-draft one to a draft, queueing the operations notice first (`draft-guard` is logged), and `retire.ts` sweeps once more before it shuts the worker down. What stays outside this is stated: a pull request from a branch other than the run branch is not attributable to the run, and the bypass is caught within a minute and at shutdown, not prevented.

Evidence in the source thread (vendor reproduce SKILL.md:214, 'Attach evidence only when the configured Slack action keeps it inside the same source thread and the organization's retention policy allows it'). The repro brief gives the worker one folder, `<control.artifact_directory>/<runId>`, for its captures, and an `evidence` array in its result (also in a rerun's) to name the files it wants attached. The worker has no Slack credential and no upload tool. `src/automation/evidence-files.ts` stages each named file in the parent: it must resolve (links and `..` followed) to a regular file inside that run folder, be a screenshot, recording or note (png, jpg, gif, webp, mp4, mov, webm, txt, md; the three artifacts the skill names, so three files), be at most `ATTACHMENT_LIMITS` in size (this package's, upstream states none) and younger than `control.artifact_retention_hours` (the retention policy upstream names), and is copied into the store so the uploaded bytes are the checked bytes. The configuration must therefore name an absolute `control.artifact_directory` and a positive `control.artifact_retention_hours`, which the template has. The reply is one `thread-reply` outbox action whose `attachments` the Slack destination uploads: `files.getUploadURLExternal` (form fields), a POST of the bytes to the returned `files.slack.com` url (without the credential), then `files.completeUploadExternal` with the reply text as `initial_comment` and the source `thread_ts`, so the reply is one message. That call returns file ids, not a message, so the action id rides in the first file's title (`<name> (pstack-action:<id>)`); `readThread` reads it back as the marker, the poster waits for it (15 reads, one second apart) and the outbox's marker check before each attempt finds a reply that landed before a crash, so no attempt uploads twice. A file the parent may not attach is skipped and logged (`evidence-staged` with each reason), and the reply then links the operations thread (`Evidence: <permalink>`, upstream's 'Link the operations evidence thread when one exists') as its fallback. A workspace that refuses uploads (`missing_scope` and the like) gets the reply as text with that link at once, and the outbox's last attempt drops the files too: evidence is optional, the one reply is not. Not done: the link is not added to a reply whose worker named no evidence.

Worker retirement. A case worker idles after its last turn, its host up for the next message. `src/automation/retire.ts` (run by the settler after the follow-up pass) shuts it down through the host's `shutdown` (`abortInTmux`) once the case's lifecycle is over: the follow-up window has closed or its `budgets.*_follow_up_minutes` has passed from the window's start (triage: the verdict; repro: the end of the fix lifecycle, `followUpAnchor`), with no repro turn and no follow-up round in flight, so a follow-up's one rerun still finds its worker. A repro case with no operations channel has no window and retires when its lifecycle ends. The decision is derived from the event log and the clock. Each attempt is a `worker-retired` entry with the abort outcome, so a restart never repeats it; a refused shutdown is retried on later passes up to `RETIRE_ATTEMPT_LIMIT` (5). Follow-up and tracker workers are not retired by this step.

Follow-up window (triage). For `budgets.triage_follow_up_minutes` after the verdict (fixed, never extended) `src/automation/follow-up.ts` reads the source thread and starts one read-only worker per batch of new human messages. The parent posts the worker's answer as a reply without a verdict marker (a reply with one is dropped), comments on the one issue the case owns, closes the window when the worker says someone asked it to stop, and aborts a worker still running when the window ends. Rounds are log entries (`follow-up-dispatched`, `-completed`, `-closed`), so a restart adopts a running worker.

Follow-up window (repro). `follow-up.ts` runs the same window for `budgets.operations_follow_up_minutes` on the operations thread (the operations root's thread, from its root), starting when the repro lifecycle is over (`repro-turns.ts` `followUpAnchor`: the report for a case that held no rejection window, the end of the fix lifecycle for one that did). With no operations channel there is no window. Each batch of human messages gets one read-only worker briefed on section 15, the recorded repro outcome, and the repro worker's directory as evidence. Its answer is posted in the operations thread without a marker. A `rerun: { correction }` in its result is the one rerun a case gets: the parent sends the correction to the idle repro worker as a turn (below), applies its status and operations reply to the operations message, and posts a source reply only when the rerun confirms a repro and the case has none. A second rerun, a busy worker, or a stopped worker is refused and logged (`follow-up-rerun-refused`).

Verdict wait and rejection window (repro). A repro event whose thread has no marker yet is `waiting`: the settler's `retryWaiting` looks again each poll, until `budgets.verdict_wait_minutes` after the event, then closes it once (`rejected` with its key). Another author's marker, an `other` verdict, or two markers close it at once. The marker's `tracker=<url>` (`verdict_markers.tracker_attribute`, an http or https link) goes into the worker's brief. When `budgets.rejection_window_minutes` is configured the brief ends the worker's first turn at the report. A report of `Reproduced` opens the window: the parent reads the source thread and sends the idle worker each batch of human messages (a review turn, as untrusted data) to answer `{ decision: continue|stop, corrected, status?, operations? }`. A `stop`, or a reply that is not that object, aborts the worker and closes the lifecycle with no fix. One correction is allowed. A status other than `Reproduced` also ends it. When the window closes with no rejection the worker is sent the go-ahead (a fix turn), bounded by `budgets.fix_minutes`, and its status and operations reply land on the operations message. A turn is a further generation of the same host (`steer`): it is logged with the host's generation before it is sent, so a generation that has not moved is sent again and one that has moved is adopted after a restart. Log entries: `repro-window`, `repro-turn`, `repro-turn-completed`, `repro-closed`. The parent cannot stop a worker that does the fix unprompted despite its brief.

Tracker url in the verdict. After the parent writes or updates the issue it rewrites the verdict's marker line to `<marker> tracker=<url>` from the landed outbox entry (the GitHub issue url, or the `url` an adapter worker returned when it is an http link), replacing any `tracker=` the worker wrote and dropping it when no issue was written. A restart posts the same text.

Attachments. The parent downloads each file of the report event (`url_private_download`, else `url_private`) into `<workerDir>/attachments/<n>-<name>` (mode 0600, the name reduced to `[A-Za-z0-9._-]`) with the Slack credential, which goes only to `https://files.slack.com` (no redirect followed; an HTML sign-in page is refused). Upstream states no limit, so the limits are this package's: 20 files, 50 MiB each, 200 MiB in all, a file cut off at its limit. A file already saved is kept. The brief lists the local paths and the reason any file is missing, and calls the content data. A failed download never stops the case. Only the report event's files are downloaded, not files in replies.

Operations thread (repro). `slack.operations_channel_id` empty disables it. Otherwise it must not be the source channel (the loader refuses it, and the outbox refuses an `ops-root` for the source channel). The worker appends status lines to `status.jsonl` in its worker directory and returns `{ text, status, operations }`. The parent posts one root (`ops-root`, marker-reconciled by searching channel history), edits it once per status change (`ops-edit`, skipped when the message already shows the text), applies the final status before the source reply, and posts `operations` as a reply in the root's thread. `Could not reproduce`, `Blocked`, and a failed worker post nothing in the source thread. The outcome is a `repro-outcome` log entry.

Tracker (`tracker.type: github`, `tracker.repo: owner/name`). `src/automation/tracker-github.ts` runs `gh api` through an injected `GhExec` (`execFile`, argv arrays, no shell). Every write carries `<!-- pstack-action:<id> -->` in the issue body or comment, and `searchByMarker` lists issues and comments updated in the last 90 days instead of using the search index, which lags writes. `update` appends to the body and `comment` adds a comment, so neither replaces unrelated fields. Create labels come from the verdict marker and `tracker.labels`, never from the worker. `src/automation/tracker-policy.ts` documents which eligibility rules are enforced in code from independent reads (marker classification, the source root in the Slack thread, resolved labels, an open target issue, the source permalink not already linked, no open same-title issue, a compensation action) and which the worker judges (clearly broken, not already fixed, whether two reports are the same). Compensation is the parent's (see Outbox above). The adapter's `close` also serves an operator.

Any other `tracker.type` (the template default is `linear`) is a project-owned adapter skill, `tracker.adapter_skill_name`, resolved like the control skill. `src/automation/tracker-adapter.ts` starts one dedicated worker per queued tracker action through `spawnAssignment` (readonly workspace, `capabilities { mcp: inherit, env: minimal, externalWrite: false }`, run id `trk-<hash(action id, attempt)>`). Its brief loads the skill and orders the work: search by the action marker first, then (create, update, comment; not the compensation close, whose issue is linked by construction) by the source permalink, write only when both find nothing, and return `{ outcome, id }`. The outcome `already-linked` is the worker's answer to the permalink search (vendor triage SKILL.md:146, 'already linked to a tracker issue'): the parent honors it by recording the action as done with `alreadyLinked`, writing nothing, starting no second worker, and putting the linked issue's url in the verdict marker line. It can only suppress a write, never cause one. The outbox entry records the worker, so a restart adopts it. A failed worker is replaced by a fresh attempt that searches the same marker first. A missing skill blocks the case (`blocked` with `problems`). The parent's tracker-side policy checks for these trackers are the worker's first steps. A worker body never carries a `Source:` line or action marker, so every `Source: <permalink>` line a tracker holds was written by the parent or by a person, and `findBySource` (the GitHub tracker's dedupe, as upstream's "already linked" check) counts any such line naming exactly that permalink, in an issue body or a comment.

Control adapter. The reproduce prerequisites `controlAdapter` and `featureMap` are `src/automation/control-adapter.ts`: the skill named by `control.skill_name` resolves from Pi's skill locations for the project (`.pi/skills`, `.agents/skills` from the project up to the repository root, `~/.pi/agent/skills`, `~/.agents/skills`, this package's `generated/skills`; the name must be plain skill-name syntax), and the file at `control.feature_map_path` is inside the project, has at least one `###` feature with no unfilled placeholder, and each feature has `How a user gets there` and `How the control adapter drives it`. `start` refuses while a source worker of that name is live. `stop` shuts down every live source worker with abort semantics and may run from any session: it is the operator's command. `status` reports the kind, live workers, attach commands, and the receiver URL.

Slash parity (spec 8.2). Each generated skill's `/name` is its `generated/prompts/<name>.md`. A name is a conflict when it is one of Pi's built-in interactive commands (`settings`, `model`, `thinking`, `scoped-models`, `login`, `logout`, `llama`, `new`, `resume`, `name`, `session`, `tree`, `fork`, `clone`, `compact`, `import`, `copy`, `export`, `share`, `bug`, `trust`, `mcp`, `reload`, `hotkeys`, `changelog`, `quit`; Pi exports no list and `get_commands` omits them), an extension command, or a prompt template from another file. For a conflict, the `input` event rewrites `/pstack:<name> <rest>` to `/skill:<name> <rest>`, the rest and images unchanged, when Pi loaded that skill; `doctor` lists each conflict. No generated name conflicts with a built-in. `/pstack:<name>` never reaches the `/pstack` command, since Pi matches extension commands by exact name.

Mid-message skill names (Cursor CLI `findSkillReferences`; the contract is recorded in `parity/pstack-parity-2026-11-05/notes.md` SKILL-REF-001..004). The `input` handler, for `rpc` and `interactive` input only, attaches, only while a pstack workflow is active, every skill that Pi loaded (`pi.getCommands()` source `skill`; pstack or not) and the message names with `/<name>` at its start or after whitespace (name not followed by `/`, `.ext`, or word characters; backtick spans and fences excluded), each once, in order of first reference. The result is Pi's own `/skill:<first> <blocks of the others>\n\n<message>` text, so Pi builds the blocks (`src/skill-block.ts` reproduces its format). A pstack workflow is active for a message when the persistent style is on for the current branch (`styleOn`), or the message invokes a pstack skill: a leading `/name`, `/skill:name`, or `/pstack:name`, or a pstack skill name mid-message. Outside that scope the input is untouched and Pi behaves natively. A leading `/skill:<name>` or a leading `/<name>` that is this package's prompt is the first skill and a message with no further name is left to Pi's template or skill expansion; a message led by a Pi built-in, an extension command, or another owner's template is not touched; a skill whose block is already in the message is not attached again.

Package manifest. `version` `0.15.36-pi.40`; `pi` as above; `files` adds `vendor`, `adapters`, and `scripts`; `peerDependencies` are the host packages the new runtime imports: `@earendil-works/pi-coding-agent`, `@earendil-works/pi-ai`, and `typebox`. The extension's import graph has no third-party module at load: the Benny config reader (`yaml`) loads only when an automation needs it, so a local `pi install` without `node_modules` loads.

## Worker process

The host runs `pi --mode rpc` in the worker's workspace with `--model`, `--thinking`, `--session-dir <workerDir>/session`, `--append-system-prompt <generated/agents/<role>.md>`, env `PSTACK_WORKER=1`, `PSTACK_RUN_ID`, `PSTACK_WORKER_ID`, `PSTACK_RUN_ROOT`, the `PSTACK_DEPTH` and `PSTACK_SPAWN` the parent put in `launch-env.json`, and the user's normal Pi resources (extensions, skills, MCP) so pstack skills and MCP are available. With `PSTACK_WORKER=1`, the pstack extension calls `registerWorkerSideTools`: only `pstack_evidence`, plus `bash_readonly` in a readonly workspace and `pstack_worker` for a sub-coordinator (`PSTACK_SPAWN=1`, see Capability boundary). Readonly workers get `--tools read,grep,find,ls,bash_readonly,pstack_evidence` plus MCP tools per capabilities. `bash_readonly` is the existing OS-sandboxed read-only shell (`src/readonly-shell.ts`, with the macOS sandbox and the Linux seccomp filter): it allows reads and network reads such as `git log` and `gh pr view`, and blocks writes and Unix sockets. The worker's pstack extension registers it when `PSTACK_READONLY=1`, which the host sets for readonly workspaces. This is the enforcement spec 12.1 requires for `how`, `why`, and reviewer workers. The proof host in `parity/pi-native-tmux-2026-11-11/proof/host.mjs` is the reference implementation. It passed 11 lifecycle gates on real processes.

## Capability boundary (spec 9.6, 14.2, 15)

`assignment.json` gains `capabilities`:

```ts
capabilities: {
  mcp: 'inherit' | 'none',          // 'none' launches pi with --no-mcp
  env: 'inherit' | 'minimal',       // 'minimal': only PATH, HOME, LANG, TERM, TMPDIR, PI_CODING_AGENT_DIR, PSTACK_* and the provider credential variables the resolved model needs
  externalWrite: false | true,      // true only for the parent or a trusted adapter; workers default false
  spawn?: boolean                   // default false. true registers pstack_worker in that worker, for Orchestrate's sub-coordinators
  forge?: boolean                   // default false. container workspaces only: true gives the worker a forge token (see Container workers, Forge access)
}
```

Default: `{ mcp: 'inherit', env: 'inherit', externalWrite: false }` for engineering roles, and `{ mcp: 'none', env: 'minimal', externalWrite: false }` for automation-dispatched workers. A `container` workspace changes only `env`: it defaults to `'minimal'` (see Container workers), whichever the role, because an upstream cloud agent holds no host credentials beyond what it is given. A worker is automation-dispatched when its `run.json` has `parentSessionFile: null`. An explicit `capabilities` object must name `mcp`, `env`, and `externalWrite`; `spawn` and `forge` are optional. `forge: true` is refused for a worktree or readonly workspace, which already runs as the operator with the operator's own `gh` login. `pstack_worker` spawn refuses `externalWrite: true`.

Sub-coordinators. A worker with `capabilities.spawn: true` is a sub-coordinator for Orchestrate. It needs `workspace.mode: 'worktree'`, and the parser refuses `spawn: true` with any other workspace: it writes its workers' assignments, and a readonly worker can write nothing. The mechanics:

- Depth. Three levels, matching upstream Orchestrate: the root chat is level 1, a sub-coordinator level 2, its workers level 3. A process's level is its `PSTACK_DEPTH`, or 1 when unset or empty; any value other than one digit from 1 to 9 fails the spawn. `spawnAssignment` computes the child's level as its own plus 1, before the write-back and the claim. It refuses every spawn when that exceeds 3, and refuses `spawn: true` when it equals 3. A refused spawn leaves no `claim/`, so the assignment can be fixed and spawned.
- Launch environment. `spawnAssignment` adds to `claim/launch-env.json`, after the env snapshot: `PSTACK_DEPTH` the child's level, for every worker; `PSTACK_SPAWN` `'1'` for a sub-coordinator and `null` otherwise, so a sub-coordinator's workers never inherit its flag; and for a sub-coordinator only, `PSTACK_TMUX_SOCKET` the parent's tmux server, so the whole tree shares one server. These are `PSTACK_*` names, so env `minimal` keeps them, and the host passes them to Pi unchanged.
- Tools. `registerWorkerSideTools(pi, env, options)` in `src/workers.ts` is what the pstack extension calls when `PSTACK_WORKER=1`: it registers `pstack_evidence` always, `bash_readonly` (from `src/readonly-shell.ts`) when `env.PSTACK_READONLY === '1'`, and `pstack_worker` (with the parent's wake watcher) only when `env.PSTACK_SPAWN === '1'`. `options` are `registerWorkerTools`'s; production passes none.
- Runs and ownership. Inside the sub-coordinator, `pstack_worker` resolves runs from `projectRoot(ctx.cwd)`, the git toplevel of its worktree, so its runs live under `<workerDir>/worktree/.pi/pstack/runs/`. It creates them with `scripts/start-run.mjs` from its `bash` tool, where Pi sets `PI_SESSION_FILE` to the worker's own session file (Pi docs, environment-variables.md, "Shell Tool Session Environment"); `start-run.mjs` writes that as `parentSessionFile`. Its `pstack_worker` checks ownership against `ctx.sessionManager.getSessionFile()`, the same file. Its wake watcher therefore delivers its workers' wakes into its own session, each starting a turn there, and its parent's watcher, which scans only the parent's runs, never sees them. The parent sees one wake per settle of the sub-coordinator, a wake-triggered turn included.

The provider credential variables are the ones pi-ai's `findEnvKeys(provider)` reports set in the parent, plus the ambient AWS and Google variables pi-ai reads for `amazon-bedrock` and `google-vertex`. A worker launched with no `--model` (an automation's `inherit-parent`) runs Pi's default model, so its provider is `defaultProvider` in `settings.json` under the agent directory the worker sees (`PI_CODING_AGENT_DIR`, else `~/.pi/agent`); when that file names none, Pi picks a provider itself, so the credential variables of every known provider (`getBuiltinProviders`) are added, still only those set in the parent. The parent passes their names in the launch argument and their current values, with any configured extra variables, in `claim/launch-env.json` (see Runtime invariants, launch environment); values never appear in argv or logs. Credentials stored by `/login` live in `auth.json` under `PI_CODING_AGENT_DIR` (default `~/.pi/agent`, found through `HOME`), and both variables survive `minimal`, so Pi still reads that file. A custom provider whose `models.json` `apiKey` is `$NAME` or `!command` gets no extra variable under `minimal`. A worker with `PSTACK_WORKER=1` gets no tool that posts to Slack, a tracker, or a forge. Only `pstack_evidence` is registered, plus `bash_readonly` for a readonly worker and `pstack_worker` for a sub-coordinator. The host enforces `mcp` and `env` at spawn. Automation credentials live in `~/.pi/agent/pstack/credentials/<connector>.json` (0600), which is never named in a brief or assignment.

The same-uid limit is stated, not hidden. A worker process running as the operator's uid can still read 0600 files that uid owns. The tool and env boundary stops a worker from posting through Pi, but it is not an OS boundary. A `container` workspace removes the limit for the worker's filesystem (see Container workers). A `worktree` or `readonly` worker keeps it, so automation setup reports it, and the parity manifest marks the credential-isolation requirement `partial` for them.

## Container workers (spec 5 "Cloud subagent", 9.6, 15.1; U10)

`workspace: { mode: 'container', inputCommit }` runs the whole worker, Pi included, in a container on the local Docker-compatible engine (OrbStack, Docker Desktop, Colima, a remote `DOCKER_HOST`). State, settle, wake, and collect are the worktree worker's. The tmux host owns the RPC pipe.

### Where Pi runs (decision)

Option 1. The tmux host stays on the host. Its child is `docker run -i ... pi --mode rpc`, so the docker client's stdio is the RPC pipe and the container holds Pi, its tools, its extensions, and the clone. Option 2, Pi on the host with only tools routed into the container, is rejected.

Evidence.
- `docs/containerization.md` (Pi 1.5.2) lists "Plain Docker" as isolating "Pi, built-in tools, `!` commands, and extensions" and the Gondolin tool-routing pattern as isolating only "built-in tools and `!` commands". It says other extension tools "still run on the host unless they also delegate", and that commands inherit the host environment, so the pattern is not "a credential boundary" without more work.
- A pstack worker loads extension tools (`pstack_evidence`, `bash_readonly`, MCP, and whatever the user installed). Under option 2 each needs its own routing. The deleted package (`2f045b2c:extensions/pi-pstack/src/cloud/routed-tools.ts`, 213 lines) routed `read`, `write`, `edit`, `find`, `grep`, `ls`, and `bash` only, and kept the Pi process and the model credentials on the host.
- Spec 5 requires "independent filesystem" for the cloud subagent and 15.1 says a worker "owns only its isolated checkout". Under option 1 the Pi process itself has none of the host's files. Under option 2 the Pi process reads `~/.pi/agent`, the project, and everything the user can.
- Measured: Pi 1.5.2 runs unchanged under the container's node (`node .../dist/bundle/cli.js --mode rpc`) with the host's install mounted read-only, loading the scripted-model fixture and this package's extension. tests/container covers it.

Isolation achieved, by test (`tests/container/container.test.ts`) unless marked.
- Host filesystem. Not visible: the worker's `test -e <host checkout>/README.md` finds nothing and it sees no engine socket. Mounted: Pi's `node_modules` (read-only, at `/opt/pstack/pi/node_modules`), this package, the role document's folder, `containerMounts` (read-only, same path), a local-path remote (read-write, same path: it stands in for the network remote, and giving the worker its push target is the point), and `<workerDir>/out` (read-write, at `<workerDir>`). The claim, `state.json`, `assignment.json`, and the control socket are not mounted. Writing in the container leaves the host checkout unchanged.
- Process. Own PID namespace, `--init`, `--cap-drop ALL`, `--security-opt no-new-privileges`, the host uid and gid (`--user`). The worker has `CapEff` zero. Files it creates in `out` belong to the host user, on every engine.
- Credentials. A worker holds its model provider's credential and, with the forge capability, one forge token (see Model authentication and Forge access). They enter through the launch-env snapshot and nowhere else. The host writes them to the docker client's stdin ahead of the RPC stream (see Entrypoint). They are absent from `docker inspect` (`Config.Env`, `Config.Cmd`, labels), from `docker history`, and from every process's argv on the host. The container does hold them, as the worker needs the provider key.
- Network. Not restricted. The container uses the engine's default bridge: the model API needs it, and it reaches the host's network services and the LAN as any bridge container does. Restricting egress is a policy the operator sets on the engine.
- Same-uid limit. The worker has no host file access, so the same-uid limit of Capability boundary does not apply to it. It still shares the engine and its kernel with every other container, and a container escape is out of scope.

### Environment

`<project>/.pi/environment.json`, read at spawn from the project checkout (the parent's, not the clone: the image must exist before the clone does): `image` (a reference), or `build: { dockerfile, context? }` relative to `<project>/.pi/` (both must resolve, by real path, inside the project: a `context` that climbs out would send that folder to the engine, and a `dockerfile` that does is refused the same way), and `install` (a shell command run in the clone before Pi). Not both `image` and `build`. Any other field, such as `start` or `terminals`, fails the spawn. A malformed file fails it too. Absent, the image is the default environment's: `node:24-bookworm` plus the GitHub CLI `gh` (a pinned release, downloaded at build and checked against its published SHA-256), built once from the Dockerfile embedded in `src/container.ts` and cached as `pstack-default:<hash of that Dockerfile>`; removing the tag rebuilds it. Any image works that has `node` (22.19 or newer, Pi's floor), `git`, `base64`, and `/bin/sh`; the entrypoint names the missing tool. An image the project names has `gh` only if the project puts it there, which a worker with the forge capability needs (see Forge access). A pulled image is resolved to its id and a built one is rebuilt (the layer cache makes that cheap), and the worker runs by id, so what ran is what was checked; the id and the engine version are in the `spawn` event. `install` runs as the worker's unprivileged user, so setup that needs root belongs in `build.dockerfile`.

Pi in the container, measured. Two ways work: bind-mount the parent's Pi install read-only (chosen), or `npm install -g @earendil-works/pi-coding-agent@<version>` in the image (4 s warm, 171 MB, needs the network and npm in the image). The mount is instant, the same Pi version as the parent, and needs no network; it needs a JS install of Pi. The mounted entry is `SpawnOptions.containerPi`, else `PSTACK_CONTAINER_PI`, else the running Pi's `process.argv[1]`, and its enclosing `node_modules` must contain `@earendil-works/pi-coding-agent`. A Pi that is a compiled binary has no JS to mount, and spawn then fails naming `PSTACK_CONTAINER_PI`; the npm-in-image route is the way around, not implemented. This package loads through `--extension <pkg>/src/extension.ts --skill <pkg>/generated/skills`, since the user's `~/.pi/agent` is deliberately absent.

### Workspace

A fresh clone made inside the container, never a bind mount of the user's checkout. The clone source is the pushed remote: `origin`, else the only remote. Spawn refuses, before any claim or container exists, when the checkout has no usable remote, when `inputCommit` names no commit in it, or when no branch or tag the remote lists is that commit or has it as an ancestor (`inputCommit <sha> is not on the remote origin ...`). Only tips this checkout holds can be compared, so a remote that moved past the checkout refuses until a fetch. The container then clones, verifies the commit is reachable, and checks out `pstack-run/<runId>/<workerId>` at the full SHA in `/tmp/workspace`, writable, so the worker can commit and push. The home is `/tmp/pstack-home` and the agent directory its `agent/`, because `/tmp` is the one place every image lets an arbitrary uid write. A worker with the forge capability authenticates https clones and pushes with its token (see Forge access). The checkout's `user.name` and `user.email` become the clone's git identity. A local-path remote (`file://` or a path) is mounted read-write at the same path. Spawn refuses, before any claim, a local remote that is the project checkout, contains it, or lies inside it (compared by real path), because the read-write mount would hand the worker the operator's checkout.

### Entrypoint

The container runs `/bin/sh -c <script> pstack-container node <pi> <args>` with the image's own entrypoint overridden. The script reads the worker's environment from stdin, one `NAME=<base64>` line per variable ended by an empty line, then clones, runs install, prints `{"type":"pstack_container_ready"}` on stdout, and `exec`s Pi, whose stdin is the rest of the pipe. Everything else it prints goes to stderr, which the host shows in the pane. The host holds Pi's RPC until the ready record arrives (up to 30 minutes, for a large install). A container that ends first fails the worker with the entrypoint's stderr as its reason. Spawn's wait defaults to 5 minutes for a container worker (`startupMs` overrides it).

The container's environment is the worker's own (the snapshot, narrowed for `minimal` as for any worker) less names that describe the host: `PATH`, `HOME`, `TMPDIR`, `PWD`, `OLDPWD`, `SHELL`, `USER`, `LOGNAME`, `HOSTNAME`, `TMUX`, `TMUX_PANE`, `PI_CODING_AGENT_DIR`, and `DOCKER_*`, `XDG_*`, `SSH_*`. The docker client gets `PATH`, `HOME`, and `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`, `DOCKER_CERT_PATH`, `DOCKER_TLS_VERIFY`, `DOCKER_API_VERSION`, which the snapshot carries for a container worker even under `minimal`, and which never reach the container. The clone's source URL, commit, branch, install command, and git identity travel as `PSTACK_CONTAINER_*` snapshot entries, because a remote URL can hold a token. The container's `--mount` arguments, name, and labels are non-secret and ride in the launch argument. A token never rides in a URL or argv. The clone URL is the remote's with any `user:token@` removed, and the host's checks of the remote use its name (`git ls-remote origin`), so the checkout's own URL stays in git's configuration. Everything the host shows or stores about a worker passes through one scrubber (`src/redact.ts`): terminal output (the tmux scrollback), `state.json` reasons, and the stderr tail that fails a worker replace every `//user:token@`, and every secret value of the worker's environment (the provider's credential variables, any variable whose name says token, secret, password, credential, API key, private, or auth, and the strings inside a JSON credential such as `PSTACK_CONTAINER_AUTH`), with `***`. Stderr is scrubbed by whole lines, so a secret split across two reads is still caught.

A container worker's `env` defaults to `'minimal'`: the container holds the resolved provider's credential (see Model authentication), the capabilities the assignment names (see Forge access), `PSTACK_*`, and `LANG` and `TERM`, and nothing else of the parent's environment. `env: 'inherit'` is honored only when the assignment names it; it passes the parent's whole environment, less the host-only names above, into the container. The default applies when `capabilities` is omitted. An explicit `capabilities` object means what it says.

### Model authentication

The container mounts an empty agent directory, so the worker's model provider needs two things from the host: that provider's credential, and the package that registers the provider. Both are resolved at spawn, before the claim, for the provider of the resolved model. A worker spawned with no model (an automation's `inherit-parent`, where `resolveModel` returns null) runs the model that `defaultProvider` and `defaultModel` in the host's `settings.json` name, passed to Pi as `--model`, because the container sees no `settings.json`; with no such pair it runs Pi's own default.

- Credential. The parent reads `auth.json` under its agent directory (`PI_CODING_AGENT_DIR`, else `~/.pi/agent`) and writes a new `auth.json` for the container that holds only that provider's entry. Nothing else in the file, and no other provider's key, is copied. It reaches the container as `PSTACK_CONTAINER_AUTH` in the launch-env snapshot over stdin (see Entrypoint). The entrypoint writes it to `$PI_CODING_AGENT_DIR/auth.json` under `umask 077` and unsets the variable before Pi starts. It is never in argv, labels, the image, or `docker inspect`, and the host's scrubber treats its strings as secrets.
- `api_key`. A literal key is copied. A key that is a `!command` or a `$VARIABLE` reference is resolved by Pi's own `ctx.modelRegistry.getApiKeyForProvider(provider)` in the parent; a caller with no registry gets `ProviderAuthUnavailable` for such a key and can pass only literal keys.
- `oauth`, investigated in Pi 1.5.2 (`pi-ai/dist/auth/resolve.js`, `pi-coding-agent/dist/core/auth-storage.js`). Pi refreshes a stored OAuth credential when less than 5 minutes remain, under a lock on `auth.json`, exchanges the refresh token, and writes the successor back, which for a rotating provider invalidates the old refresh token. A container that held the host's refresh token would rotate it into a file the host never reads and log the operator out. So the container gets `{ type: 'oauth', access, refresh: '', expires }`: the access token and an empty refresh token. Pi's `toAuth` derives request auth from the access token alone, so the worker authenticates without a refresh token.
- Before spawn. When the stored token has less than 10 minutes left (`MIN_OAUTH_LIFETIME_MS`, `SpawnOptions.minOAuthValidityMs`), the parent has its own model registry resolve the provider's credential, which refreshes it on the host through Pi's normal path, and re-reads `auth.json`. When the token still has less than 10 minutes left (Pi refreshes only inside the last 5, so a token with 5 to 10 minutes left is refused until it rolls over), or there is no registry to refresh with, spawn fails before any claim with `ProviderAuthUnavailable: the stored OAuth token for <provider> expires in N min, and a container worker cannot refresh it`.
- At expiry. The worker's lifetime is bounded by the access token's: a token with T left at spawn serves a worker for about T minus 5 minutes. After that Pi in the container attempts a refresh with an empty refresh token, the provider refuses it, and the worker's model call fails with `OAuth refresh failed for <provider>: ...`; the host settles it `failed` with that reason. No refresh token has left the host, and the host's `auth.json` is unchanged. Measured on the real `claude-subscription` provider: `OAuth refresh failed for claude-subscription: Token refresh failed: Bad Request`. A long program therefore spawns workers per unit and does not rely on one worker outliving its token. The host does not refresh a running worker's token.
- Provider packages. A provider Pi has built in (`getBuiltinProviders`, such as `deepseek`) needs none. Any other provider with a stored credential needs the Pi package that registers it, because the container's Pi has no packages of its own. The parent looks in the user's and the project's `settings.json` `packages` (`npm:` sources under `<agentDir>/npm/node_modules` or `<project>/.pi/npm/node_modules`, and local paths) for a package whose source calls `registerProvider(` and names the provider id. It mounts that package read-only at the same path, with the dependencies its `package.json` resolves outside itself, and adds each of the package's `pi.extensions` to Pi's `--extension` arguments. `SpawnOptions.containerProviderPackages` or `PSTACK_CONTAINER_PROVIDER_PACKAGES` (a path list) replaces the search. Git sources and providers defined only in `models.json` are not found; a stored credential for a provider with no package fails the spawn with `ProviderAuthUnavailable` naming the override. A provider with no stored credential (keyed by an environment variable, or keyless) gets no `auth.json` and no package, as before.
- Tested. `tests/container/provider-auth.test.ts` runs a fixture provider package in the container: the worker authenticates with exactly the access token it was handed, its `auth.json` holds the one provider with `refresh: ''`, no decoy credential or host refresh token reaches it, and the host `auth.json` is byte-identical afterwards. It also covers the host refresh through a registry, the refusal near expiry, and the empty-refresh attempt at expiry. `tests/container/container-auth.test.ts` covers the decisions without an engine. `tests/container/model-smoke.test.ts` (opt-in, `PSTACK_E2E_REAL_MODELS=1`) sends one prompt to `deepseek/deepseek-flash` (`api_key`) and `claude-subscription/claude-sonnet-5-5` (OAuth) from inside a container, and the expiry case on the real provider.

### Forge access

An upstream cloud agent has no host credentials beyond a push token. A container worker gets that token only when its assignment says `capabilities.forge: true`, and only the token, never the operator's `~/.config/gh` or keyring.

- Source. At spawn the parent reads `PSTACK_CONTAINER_FORGE_TOKEN` from its environment (a token the operator scoped for workers, such as a fine-grained one, preferred), else runs `gh auth token`, with only the variables `gh` reads (`PATH`, `HOME`, `GH_*`, `GITHUB_*` tokens and host, `GH_CONFIG_DIR`, `XDG_*`). A `gh` login holds the operator's own scopes and cannot be narrowed here, so the operator who wants less sets `PSTACK_CONTAINER_FORGE_TOKEN`.
- Preflight. Before any claim, spawn fails with an error starting `ForgeUnavailable` when there is no token source (no `gh` on PATH and no override, or `gh auth token` fails or prints nothing), or when the image has no `gh` (a `docker run ... command -v gh` against the resolved image; the default image always has it).
- Delivery. The token travels in the launch-env snapshot under `GH_TOKEN`, so it reaches the container over stdin and nowhere else (not argv, labels, image, `docker inspect`, or a file). `GH_TOKEN` is added to the worker's credential names so `env: 'minimal'` lets it through. A worker without the capability never gets `GH_TOKEN` or `GITHUB_TOKEN` under `minimal`, whatever the parent's environment holds.
- Use. `gh` reads `GH_TOKEN`. The entrypoint also installs a git credential helper for `https://<host>`, where the host is the parent's `GH_HOST`, else `github.com`, so `git clone` and `git push` over https authenticate with it. The helper answers for that one host only, so the token goes to no other.
- Tested (`tests/container/forge.test.ts`) against a real git smart-HTTP server over TLS that requires the token for pushes: a worker without the capability is refused, a worker with it pushes and the ref lands in the bare repository, `gh auth status` reports the `GH_TOKEN` source, and the token is absent from `docker inspect`, `docker history`, the image, and host argv. The same file covers the three preflight refusals.

### Outputs

`<workerDir>/out` is mounted at `<workerDir>` inside, so the brief's paths are the same in both places. The host links `session`, `evidence`, and `report.md` in the worker directory to `out/`, so every reader of the worker directory sees the live files. `collect` reads `report.md`, the session file, and the evidence list from `out` itself, never through the host links, and never follows a symlink: every directory on the path must be a plain directory (`lstat`), the file is opened with `O_NOFOLLOW`, must be a regular file (`fstat`), and the path must still resolve to the very file that was opened (so a component swapped for a symlink between the check and the open is refused, not followed). A report that is a symlink reads `(refused: report.md leaves the worker output directory)`; a session file that is one gives no final text; the evidence listing skips every symlink, whatever it points at, and does not descend into a symlinked directory, so `evidence/x -> /` is never walked (`src/untrusted-output.ts`, `tests/container/untrusted-output.test.ts`, and a container worker that plants such links). The worker controls that directory, so nothing here trusts a check made earlier than the read it guards.

### Receipts

The verifier records its own receipt. Inside a container (`PSTACK_CONTAINER=1`, set by the host) the run root is not mounted, so `pstack_evidence` works on the worker's directory instead: `record` writes `<workerDir>/receipts/<id>.json` (host path `<workerDir>/out/receipts/`, the inbox), refusing a receipt or an artifact outside the worker's own directory, with the contract's rules unchanged (its own temporary file hard-linked to the receipt name, an identical re-record a no-op, a different receipt under a recorded id an error). `verify` and `list` read that inbox. The worker saves receipt and artifact files under `evidence/` as before; paths are the same strings on both sides.

The host takes the inbox into the run (`ingestContainerReceipts`, run by every host `list`, `verify`, `/pstack` command read, and by `collect` of a container worker, so the order of those calls cannot matter). For each inbox file it reads without following a symlink (see Outputs), parses it as a receipt of this run whose id is its file name, and requires every artifact to lie in that worker's directory. It then stores a new file of its own as `verification/receipts/<id>.json` by the same exclusive hard link, with `receiptPath` naming the inbox file and `recordedAt` the host's time. It never links the worker's file, because the worker could keep rewriting that inode. Ingesting again is a no-op; an id already recorded with different content, a symlink, a malformed file, or an artifact outside the worker's directory is rejected, and the rejection is reported by `collect`, `list`, and, when no receipt matches, `verify`'s inconclusive reason. A recorded receipt is never replaced. `verifyTarget` hashes artifacts through a no-follow, non-blocking open and treats a non-regular file as a defect.

### Lifecycle

- Name and label: the container is named for the worker's tmux session (`pstack_<runId>_<workerId>_<hash>`, which carries the project hash, so it is collision-free) and labelled `pstack.worker=<session>` and `pstack.run=<runId>`. pstack lists and removes containers by those labels only, never by name alone.
- It runs `--rm` and ends with its stdin. Shutdown, abort, and `SIGHUP` close the pipe, Pi exits, and the container goes. The host then removes by label to confirm, before the settle that records the stop.
- A host that dies without cleanup (`SIGKILL`) closes the same pipe, so the container ends; tested.
- `abort` also removes by label after the host's answer or its absence, so an unreachable host leaves nothing; an `abandoned` worker never had a container. It removes on the engine spawn recorded, not the one the environment names when abort runs: spawn writes `claim/engine.json` (0600, exclusive, before the host starts) with the docker client path and the client's `PATH`, `HOME`, and `DOCKER_*` snapshot, and abort reads it (`removeRecordedContainers`). A container worker with a claim but no record gets a `container_removal_failed` event saying the engine is unknown; it never guesses one from the current environment.
- A settled worker is idle, and its container stays until `abort` or the host ends, as a worktree worker's Pi does. `collect` stops nothing.
- Each removal is an event: `container_removed` or `container_removal_failed`. Removal is idempotent: it lists by label and removes what it finds.
- `ContainerUnavailable` (the error text starts with that name) is raised in the parent before the claim for every refusal that means a container worker cannot run this assignment here: no `docker` answers `docker version`, the project has no usable remote (none, or several without `origin`, or a local remote that is or contains the checkout), `inputCommit` is not on the remote or the remote cannot be read, or the image cannot be pulled or built. A swarm step that names a worktree fallback takes it on any of these. A malformed assignment (an `inputCommit` that names no commit, a bad `.pi/environment.json`) keeps its own message, and `ForgeUnavailable` stays separate. All leave no claim.

## Webhook routines (spec 14.4)

`createRoutine(config, { spawnWorker })` and `startRoutineSource(routine, { credentialFile, port?, maxBodyBytes? })` are exported by `adapters/automation-events.ts`. A routine config has `kind: 'routine'`, `name`, `prompt`, and `projectRoot`, with optional `model`, `thinkingLevel`, and `capabilities`. It is separate from Benny's Slack case model. Each accepted event dispatches a fresh `kind: 'pi'`, `role: 'general'` worker in a readonly project workspace. Default capabilities are `{ mcp: 'inherit', env: 'minimal', externalWrite: false }`. The operator can override capabilities in the routine config.

`node scripts/routine-setup.mjs --project <root> --name <slug> --prompt-file <file>` creates `<project>/.pi/pstack/automation/<name>/config.json` without replacing existing configuration. Conflicts fail. Setup creates or reuses `~/.pi/agent/pstack/credentials/<name>.json` with mode `0600`. It reports the credential path, never the key. The UI server reads its `key` field directly. `--serve` starts the receiver and reports its actual URL. The default port is 47913. `--port 0` chooses an available port. Keep the server process running. Remote deployments run the receiver on the remote host behind a trusted proxy.

The receiver accepts `POST /events` with a JSON object and either `Authorization: Bearer <key>` or `X-Automation-Key`. Bodies over 64 KiB receive 413. Invalid keys receive 401. Authentication headers never enter event storage, assignments, briefs, or logs. Only `content-type` and `user-agent` enter the wake. The brief contains the operator's prompt, a `[routine]` marker, and a JSON `<webhook_event>` block with `headers`, `body_digest` as SHA-256 of the raw body, `body` as the raw JSON string, and `timestamp_ms` as receiver time. The block is untrusted data. Less-than characters are escaped so body text cannot close the block.

`X-Automation-Event-Id`, when present, identifies an event indefinitely within that routine. Reusing it with a different body still keeps the first event. Otherwise the key is the raw body digest plus `floor(timestamp_ms / 60000)`. Identical bodies in the same fixed one-minute window are duplicates. Identical bodies across a window boundary are new events. Send an explicit event id for retry-safe delivery across boundaries or to distinguish identical clicks. Accepted events persist before dispatch. Source startup reconciles pending events. A completed dispatch returns HTTP 200; duplicate dispatches return 200 without another worker. A dispatch failure returns 503 for retry. Routine workers do not use Benny's reply outbox.

The same-uid credential limitation above still applies. This is not OS credential isolation.

## Runtime invariants (third design, after two rejected rounds)

- Settle coverage: after `agent_settled`, the host sends RPC `get_state`. A settle covers exactly the generations acknowledged and the runs settled that the host had observed when it sent that `get_state` (see Settle coverage rule, fourth revision), and only when the response shows `isStreaming: false` and `pendingMessageCount: 0`. Otherwise the settle covers nothing and the host waits for the next one. Recording is idempotent, because checks overlap and their answers can arrive in any order. The host counts runs (each `agent_settled`) as it counts generations. A check records only when, as its response is handled, a run or a generation it covers is not yet covered, and it records the latest unrecorded run's outcome when there is one. A later check finds everything covered and records nothing.
- Settle liveness: a run's `agent_settled` records its outcome, and when its quiescence check finds Pi busy the outcome stays unrecorded. Every later quiescent transition that is not a run's settle starts the same check: `compaction_end`, `auto_retry_end`, a `handled` response, any other successful acknowledgement while no run is in progress, and the host's own cancel completion (after `clear_queue`, `abort`, and a quiescent `get_state`). Such a check records a settle only when acknowledged work exceeds the latest settle's generation, with the unrecorded outcome, or else `idle` (compaction, retry), `handled`, the latest run's outcome (an acknowledgement that arrived after its run settled), or `aborted` (cancel). No path waits for another `agent_settled`.
- Handled prompts: a prompt, steer, or follow-up that Pi answers with disposition `handled` (an extension command) starts no run, so no `agent_settled` follows it. Its generation counts as acknowledged, and the response handler starts the same `get_state` quiescence check. When Pi is quiescent, the host records a settle with phase `handled` covering it; when a run is active, that run's settle covers it. The parent's wake for it says the worker handled its prompt as a command.
- tmux identity: `new-session -P -F '#{pid} #{start_time} #{session_id} #{session_created}'` is recorded in `claim/tmux.json`. Abort's fallback lists the same format, matches all four, and kills `-t <session_id>` inside `if-shell -F` on the same condition, so the check and the kill are one server command. Otherwise it refuses. The server pid and start time are needed because tmux 3.8 exits with its last session and a restarted server hands out `$0` again: a foreign session created in the same second gets the same `#{session_id} #{session_created}` pair (observed 2026-11-11: `$0 1794450293` before and after a restart, server pids 12102 and 12107).
- Spawn outcome: `new-session` exiting with an error created nothing, so spawn removes `claim/`. A killed or timed-out tmux client, a thrown exec, or a success without a parsable identity is an unknown outcome, and the claim stays until evidence settles it: spawn lists `#{session_name} #{pane_pid}` with the four-field identity and reads `claim/identity.json`. A claim proves the host started, and the session whose pane pid is the claim's host pid supplies `tmux.json`. Only when the bounded wait (`startCheckMs`, default 10 s) ends with no claim and no session by the worker's name is non-start established and `claim/` removed. A session by that name with no claim leaves the outcome unknown: spawn fails and the claim stays.
- Launch environment: `claim/launch-env.json` is the worker's complete environment before the `PSTACK_*` identity variables, taken from the parent at spawn time. For env `inherit` it is every variable the parent has, plus configured extra variables. For env `minimal` it names every allowed variable (the minimal set, the provider's credential variables, and the parent's `PSTACK_*`), with `null` for each one the parent does not have. In both modes the parent then sets `PSTACK_DEPTH`, `PSTACK_SPAWN`, and for a sub-coordinator `PSTACK_TMUX_SOCKET` (see Capability boundary, Sub-coordinators). The host builds the child's environment from this file alone, never from its own `process.env`, which tmux gives it from the tmux server's environment at server start (tmux 3.8 passes only the client's `PATH`).
- Launch secrets: credential values and any extra env go in `<workerDir>/claim/launch-env.json` (0600, created exclusively), which the host reads once and unlinks before spawning Pi. Never argv, never logs. The parent removes it on every exit from spawn after writing it, whether the identity parse, the `tmux.json` write, the event append, or the handshake failed; that cleanup never removes `claim/`, which only established non-start does. A host that dies after writing `identity.json` and before reading the file, with its parent gone too, leaves it behind. Abort of an unanswering host removes it once it establishes that host can never run again: no session on the server matches the four-field identity in `tmux.json`, and no live process has the claim's host pid with the process start time `identity.json` records (see Host identity for secret cleanup). While that host may be live, or with no `tmux.json` to check, the file stays.
- Worktrees: the host creates `worktree/` under its claim. A pre-existing path is refused; there is no reuse.
- Wake delivery after compaction: the delivery record is the active branch from `getBranch()`, compacted entries included, so a wake summarized by compaction counts as delivered. Each branch change increments a branch version. A poll started under an older version discards its result and reruns.

## Settle coverage rule (fourth revision, from Pi source)

Pi's RPC mode handles each stdin line concurrently (`rpc-mode.js` `void handleInputLine(line)`), and a `prompt` answers later through `preflightResult`. Responses are therefore not ordered with respect to other commands. A quiescence check covers only the generations whose acknowledgement and the runs whose `agent_settled` the host had observed **before it sent that `get_state`**. Pi emitted those acknowledgements before handling the later `get_state`, so its snapshot includes them. A reply never covers work observed after its request was sent. An acknowledgement that arrives while no later check is pending and the host is idle triggers a new check. Every check in flight when an acknowledgement arrives was sent before it, so a successful acknowledgement received while no run is in progress (no `agent_start` without its `agent_settled`) starts a new check; a `handled` one starts its `handled` check instead.

A reply records nothing when a run started or settled after its request was sent. Pi's `_emitAgentSettled` (`agent-session.js`) clears `_isAgentRunActive` before it awaits the extensions' `agent_settled` handlers and emits the event, so a quiescent snapshot can reach stdout after that run's `agent_start` and before its `agent_settled`. Such a snapshot may count the run's work as done without its outcome. The run's own check, sent on its `agent_settled`, records it. Overlapping checks therefore give the same settles whichever answer arrives first.

Default-provider credentials: when the model is `inherit-parent` and no `defaultProvider` resolves, `env: minimal` keeps every known provider credential variable present in the parent (pi-ai `findEnvKeys` over all providers, plus the Bedrock and Vertex ambient variables), and still drops all non-credential variables.

Host identity for secret cleanup: `identity.json` records the host pid and its process start time. A pid counts as the host only if it is alive with the same start time. The host and the parent read the start time with the same function, `processStartTime` in `src/run-files.ts`: on Linux, field 22 (`starttime`, clock ticks after boot) of `/proc/<pid>/stat`; elsewhere, `ps -o lstart= -p <pid>` with `TZ=UTC` and `LC_ALL=C`, so both read the same text whatever their own environment. `lstart` has one-second resolution, so on macOS a pid reused within the second the host started still counts as the host and the file stays. The host's command line plays no part, so an assignment path with spaces or non-ASCII characters needs no matching.

Ambient Bedrock configuration: `AWS_REGION` and `AWS_DEFAULT_REGION` are kept under `env: minimal` with the Bedrock credential variables. They are not secrets, and pi-ai's credential check does not read them, but the Bedrock client needs a region to make any request. Dropping them would break a minimal Bedrock worker without hiding anything.

A settle needs something collectable (judge U04a7 B, corrected). A new run counts once any prompt has been acknowledged, because an extension can start a turn with no RPC prompt: a child's wake to a sub-coordinator triggers one through `sendMessage`. A run that settles before the first prompt's acknowledgement records nothing, and the acknowledgement's own check records it with that run's outcome. The judge's premise, that every run follows an acknowledged prompt, was false for extension-triggered turns. tests/worker-lifecycle/nested-spawn.test.ts caught it.

Host liveness for secret cleanup needs positive evidence (judge U04a7 D). A dead pid, or a live pid with a different start time, is gone. A live pid whose start time cannot be read is treated as the host, and its `launch-env.json` stays.
